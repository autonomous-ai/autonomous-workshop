- [kernel · repair · huggy 2026-08-11 · cost 1 repair pass · GRADUATED→blocks.rounded_box] Never fillet ALL three edge directions of a box (top + bottom + vertical) at any single corner — whether via one blanket `.edges().fillet(r)` or several chained per-selector fillets that together still cover every corner. OCCT must synthesize a spherical vertex-blend there, and in this environment that blend tessellates to a degenerate zero-area sliver triangle disconnected from the main mesh (~8 phantom bodies per fully-filleted box), passing `is_solid`/no-error checks yet failing the watertight/bodies gate — reproduced with a bare `cq.Workplane("XY").box(10,10,10).edges().fillet(1)`, so it's not fixable by adjusting radius, order, or mesh tolerance. Fix: bake vertical-corner rounding into the 2D profile (arcs via a rounded-rect wire, then `.extrude()`) so no sharp vertex remains, and apply any additional top/bottom-only fillets afterward — those two edge loops never share a vertex with each other so no vertex-blend is ever built (Huggy 2026-08-11 repair).

- [tooling · build · draft-stack-dock 2026-08-12 · cost 1 repair tier · OPEN] A periodic perpendicular cross-tie grid added only to defeat the gate's flat-quad mesh-tessellation false positive (a long thin down-facing gap between parallel ribs meshes as 2 giant sliver triangles whose centroid reads as far-from-boundary, tripping bridge_span even when the true gap is safe) has a narrow, non-negotiable safe-density window, not a dial you can loosen for cosmetics: draft-stack-dock's z=0-6 "7 front-to-back flow ribs" (brief: uni-directional, no cross members) needed cross-ties every ~17mm pitch to hold bridge_span at 19.2mm — 22mm pitch already only barely passed (24.5mm), and 30mm pitch failed outright (25.6mm). That safe density inescapably reads as a two-directional waffle grid to a fidelity reviewer even though it's structurally sound; restructuring the connectors to be scoped per-gap instead of full-width bars (tried in this repair) changes NOTHING visually or volumetrically, since both approaches only add material inside the open gaps — the full-width portion crossing already-solid rib material was always a no-op union. A repair pass (construction-only, no redesign) cannot buy back this mismatch by thinning tie density; it will just re-fail the gate. This has to be solved at BUILD time with a genuinely different construction for any brief-mandated uni-directional rib/slat feature — e.g. a shallow non-planar (grooved) underside profile running the SAME direction as the ribs, so OCCT's mesher is forced to add interior vertices without introducing a perpendicular structure — instead of defaulting to perpendicular cross-ties as the fix for this false-positive class.

- [discipline · repair · draft-stack-dock 2026-08-13 · cost 1 repair tier (2nd recurrence) · GRADUATED→gate.stale_stl] The "re-export before trusting a gate verdict" lesson above was already written down and got ignored again the very next session on the SAME part: draft-stack-dock's next repair inherited a `gate.json` (`not_watertight`, `fit_check_failed`) that was stale by 12 minutes against `main.py`'s last edit — `stat` on `main.py`/`draft-stack-dock.stl`/`gate.json` showed `main.py` saved AFTER the STL/step export, and gate ran right after that without a re-export in between. Root cause of why re-export got skipped: this part's `gen_step()` takes ~65s (many chained unions/cuts), but `scripts/cad`'s default `--wall-clock-s` is 30 — a plain `cad .` call SANDBOX_TIMEOUTs, and it's easy to read that as "can't re-export right now" and move on to editing/diagnosing instead of retrying with a longer timeout, leaving the stale STL in place for the gate to score. Two takeaways: (1) treat a lesson that repeats as a signal to graduate it — a session-start check comparing `mtime(main.py) > mtime(<slug>.stl)` (or gate.py refusing to score a stale STL) would have caught this mechanically instead of depending on the agent remembering prose guidance twice; (2) if `scripts/cad` SANDBOX_TIMEOUTs on a part with many chained boolean ops, retry with `--wall-clock-s <bigger>` (e.g. 180) before assuming the build is broken — a timeout is not a build failure, and moving on without a successful export is how a gate verdict goes stale.

- [kernel · repair · draft-stack-dock 2026-08-13 · cost 1 repair tier · OPEN] Never let an independently-built rib/tie boundary be trimmed against a surface that ANOTHER cutter has already carved edges into — give it a standoff instead. draft-stack-dock (2026-08-13) failed `not_watertight` on 16 non-manifold triangles because `build_plenum_ribs` runs fixed-X ribs straight across the flue, so a rib's flat side face at |x| = DECK_RIB_PITCH + DECK_RIB_T/2 = 25.2 was trimmed against the flue's outer cone — and that trim curve's angular position sweeps 36.5° (z=8.4) → 30.4° (z=16.1), passing within **0.011°** of the lattice's own column-1 window edge at 35.653°. Two independently-built CUT BOUNDARIES that near each other make OCCT place a facet vertex 0.005mm from the trim edge and emit zero-area sliver triangles (measured: 0.001mm² faces at (25.200,18.077,9.568) vs (25.205,18.080,9.568)) — `isSolid` stays true, the STEP looks fine, and only the STL is broken. Rotating the pattern only relocates the coincidence, because the crossing curve sweeps through every window-edge angle somewhere in z; the categorical fix is a `flue_clearance_cutter`-style offset-surface standoff subtracted from every rib/tie piece before union (same technique as the existing `corner_clearance_cutter`), so a rib boundary can never reach the cut-up surface at all. Crucially, do NOT then chase every remaining tangency: a boundary merely GRAZING one smooth revolved surface is benign (verified — 2mm standoff leaves the 25.2 rib face tangent at z≈38 and a cross-tie face tangent at z≈35.6, and the mesh still measures 0 broken faces / 0 non-manifold edges), and the only gaps that remove all tangency here were 9.4–14.8mm, big enough to reopen the deck's bridge span. The hazard is boundary-on-boundary, not boundary-on-surface. Corollary caught the same round: a plug/boss meant to swallow another solid's edge must STRICTLY contain it — the flue-mouth floor plug was `FLUE_MOUTH_D/2 + 2.0` == 32.0 == exactly `flue_radius(FLUE_Z0, True)`, i.e. the flue's bottom edge circle sat precisely on the plug's rim; use `+ WALL_FLUE + 1.0` so it is buried 1mm inside.

- [assembly · repair · arc-coil-blaster-prop 2026-08-13 · cost 1 repair tier · OPEN] When adding hidden internal support ribs/gussets to fix a bridge-span finding, first map out every OTHER part that shares the same local volume in the assembled pose — a construction-only fix that ignores this can silently trade one gate failure for a worse one (or a new collision) the gate doesn't even check by default. arc-coil-blaster-prop (2026-08-13): the printability lens correctly found index_wheel's flat "cup form" web bridging 28.8mm unsupported (gate's own inscribed-circle heuristic undercounted it as 16.5mm because 6 isolated lightening holes fragment the visible area without touching either support boundary). The obvious fix — hidden radial ribs from the axle hub out to the rim, filling the hollow rim tube the web caps — is correct in spirit but a naive full-radius version collided with the CARRIER's ratchet hub, which (via the assembled pose's Y-offset math) pokes a full-360° r=23mm cylinder into that exact hollow for that part's entire rim height; the `cad` tool's own assembly-interference check caught it (6330mm^3 overlap) even though gate.py (mesh-only, no cross-part checks) would have passed the STL standalone. A second hard constraint stacked on top: the wheel's drive_pawl is a COMPLIANT FLEXURE (not a rigid mount) over a specific angular arc — fusing rib material there would rigidify it and break the ratchet-and-pawl indexing mechanism, a functional must-have no mesh gate can detect either. Fix was a single C-shaped washer gusset, inner radius = ratchet hub radius + 2mm clearance, outer radius = 1mm into the rim's solid band, angular extent = full circle minus the flexure arm's sweep (with ~10deg margin) — verified with BOTH gate.py (bridge_span 28.8->16.5) AND a full assembly re-export through the `cad` tool (no collision warning) before trusting the fix. Lesson: a bridge/void fix that adds material to a "hollow" region must be checked against (a) every OTHER part whose assembled envelope reaches into that same local space, via the `cad` tool's interference check, not just gate.py's single-part mesh stats, and (b) any COMPLIANT/flexure feature whose motion depends on that region staying unfused.

- [brief · repair · scram-rod-drop-desk-switch 2026-08-17 · cost 1 repair tier (FUNCTIONAL 2/3, plus the round before it) · OPEN→belongs in BRIEF] When a brief puts a MOVING indicator behind a window and a falling/sliding member inside the same enclosure, check at brief-authoring time that the indicator's HIDDEN position clears the mover's swept column — checking only its showing position is what ships an object whose headline motion cannot happen. Two lines of arithmetic settle it for a two-state rocker readout: the legend that SHOWS sits at (Yp + r, Zp) and, because the window's own z band is inside the mover's travel, its back face must be in FRONT of the column (r >= col_half + clr - Yp); the SAME lobe in the other state sits 2*swing away, at z = Zp + r*sin(2*swing + half_tile), which must stay under the mover's contact height AND inside the cavity. Second, cheaper test from the same failure: a W-wide legend can only live in an x band no mover crosses, and three Ø16 feet at pitch 26 leave only 10mm gaps, so a briefed 22-wide tile behind a centred window ALWAYS sits in the middle rod's column (measured: 266mm3 of the showing tile inside the rod at the briefed 24mm drop).
