# ADR 0022: Blind signature review before final verification

- Status: Accepted
- Date: 2026-08-30
- Owners: Inventor roster, Make, Release, product-run instruction, and public archive maintainers
- Relates to: ADR 0019 (Spark economics), ADR 0020 (signature evidence), ADR 0021 (Spark compaction and review)
- Supersedes for new runs: ADR 0021's prompted signature-review protocol

## Context

Mooncoil Dragon was the first permanent production Spark challenger under the
v2 compaction policy and signature-review contract. It completed and published
in one Make attempt and one Release attempt, but still used 7,468,236 gross
input tokens over 44 minutes 43 seconds. Make accounted for 5,734,110 input
tokens; Release accounted for 1,734,126. Relative to Pocket Eclipse Menagerie,
Release input fell about 61.5%, evidence that native compaction and the smaller
manual path helped. Make input rose about 66%, however, because visual repair,
rebuild, rendering, and full verification repeated inside the same Goal.

The final manual was concise, product-specific, and visually strong. The final
product was not. Its signature sheet showed two states, but the intended
crescent-and-castle negative-space reveal remained obstructed by the dragon's
large central mass. The critic had received the Wish and concept, named the
same risk, and still affirmed both readability booleans. The evidence proved a
prompted confirmation, not an independent read.

Inventor selection also treated the rocking motion as the central magic and
selected a mechanism specialist. The Wish's hard problem was instead a
perceptual two-truth reveal; rocking was only its carrier. Finally, Make ran
expensive complete verification while the visual proposition was still moving,
preserved the same final render family in two locations, and Release created
three complete manual review directories despite needing only initial and
final packets.

## Decision

New materialized Make finalizers require schema-v2
`<cad-project>/snap/SIGNATURE-REVIEW.json`. A bounded independent native critic
first receives only the exact candidate `iso.png` and `signature.png`: no Wish,
title, concept, desired nouns, Inventor, or intended answer. It records what
physical object and state change or outcome it sees without prompting, and
whether the artifact looks like a desirable finished product. Only afterward
does the root Manager reveal the Wish and compare that blind read with the
promised held form and signature experience.

The finalizer verifies the exact canonical fields, affirmative declarations,
and final image hashes. It does not interpret prose or assign a beauty score.
Semantic and aesthetic judgment remains native-agent work; Python remains a
typed evidence boundary.

Make changes its verification funnel:

1. build a plausible exact draft and run narrow build and geometry checks;
2. render and conduct the blind signature review;
3. if needed, resolve the single largest visual defect and conduct one focused
   blind rereview;
4. batch stable exports and run the integrated full verifier once;
5. finalize one canonical `snap/` family under the declared CAD project.

The full verifier is not a visual-design inner loop. The Make finalizer rejects
duplicate final hero, signature, or review files outside the declared CAD
project. Iteration renders remain unsealed private work.

Inventor Taste descriptions must distinguish ownership of the core magic from
ownership of a carrier mechanism. Pico Press now owns products where push,
spin, roll, or wobble mechanics are themselves the magic; silhouette, aperture,
shadow, and story transformations route to the specialist whose perceptual
method owns the reveal.

Release uses exactly two complete manual review packets: `review-v1`, then
`review-final` after one coherent revision. Evidence-only JSON work does not
cause another PDF render. This is a product-run budget instruction, not a host
aesthetic gate.

## Alternatives considered

### Tell the critic the desired answer more forcefully

Rejected. More priming makes agreement easier while providing less evidence
that a customer will perceive the intended experience unaided.

### Add a Python vision model or beauty score

Rejected. That would create host-owned cognitive judgment and undermine the
native-agent boundary. The host verifies exact evidence; it does not decide
what an image means.

### Run full CAD verification after every visual edit

Rejected. Narrow checks are sufficient while design relationships are moving.
The complete verifier belongs once at the stable final-candidate boundary.

## Consequences

- A signature-review pass now means the intended object and experience survived
  an unprimed read, not merely that a critic agreed with supplied nouns.
- Visual failure is discovered before the most expensive deterministic CAD
  pass, when one focused geometry repair is still affordable.
- Public archives preserve one authoritative final render family instead of
  identical copies that obscure the actual decision trail.
- Inventor selection is less likely to confuse a transport mechanism with the
  Wish's defining creative problem.
- Release retains an independent visual edit without paying for unbounded
  complete render rounds.

## Compatibility and migration

The finalizer and product-run instructions are copied into each run. Frozen
older runs retain their schema-v1 review and original instructions when
resumed. New runs receive schema v2. Public schema-v1 toy snapshots remain
truthful historical evidence and require no rewrite.

## Verification

- Finalizer tests reject missing, non-canonical, false, stale, and duplicate
  schema-v2 signature evidence.
- Spark, Forge, and Quest deterministic end-to-end runs pass the new exact
  finalizer.
- Skill-lock and package tests bind the revised CAD and manual instructions.
- A permanent production challenger must demonstrate an unmistakable blind
  signature read while reducing Make input from Mooncoil Dragon's 5,734,110
  and continuing toward the 2,461,602 whole-run gross-input target.
