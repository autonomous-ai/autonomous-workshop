## ADDED Requirements

### Requirement: Make consumes only the normalized sealed Concept

For a new run with simplified authoring, the Make packet SHALL bind the exact normalized sealed Concept, Concept effect evidence, accepted Invented identity, ordered `required_product_component_keys`, and a bounded summary of no more than 20 sealed visual roles. Make SHALL NOT parse, reinterpret, or depend directly on the raw consolidated source or visual-plan file layout.

The normalized physical brief and its build-critical numerical constraints SHALL be authoritative. Adaptive Concept images SHALL communicate intended form, state, action, and relationships but SHALL remain non-evidentiary. A missing agent-authored derived Wish SHALL NOT create a Make need because routed-Wish preservation is a deterministic normalized binding.

#### Scenario: Simplified Concept reaches Make
- **WHEN** the host prepares Make after an accepted simplified Invent checkpoint
- **THEN** Make receives the normalized sealed contract, effect receipt, and stable component keys through the same durable handoff class as other marked runs

#### Scenario: Raw authoring layout changes
- **WHEN** a compatible finalizer changes how its two native source files are serialized without changing the normalized sealed contract
- **THEN** Make behavior and its product contract remain unchanged

### Requirement: Adaptive visual roles guide but do not replace Make proof

The routed Make instructions SHALL identify `primary-form`, every `signature-experience` role, and any need-driven assembly or component roles from the sealed Concept. Make SHALL use those images only as design direction and SHALL freshly author CAD, generate exact product states, render the canonical product images, perform blind semantic review, and run the current deterministic verification funnel.

Make MUST NOT require absent fixed `front`, `top`, `bottom`, `exploded`, or per-component images when the accepted adaptive plan did not declare them. It MUST NOT copy any Concept image bytes into the product tree.

#### Scenario: One-piece Concept omits exploded view
- **WHEN** Make receives a valid two-role one-piece Concept
- **THEN** it builds and verifies the product without inventing an exploded Concept requirement

#### Scenario: Signature image exists
- **WHEN** a Concept signature role depicts the promised transformation
- **THEN** Make still proves that transformation from distinct exact CAD states and its own fresh render evidence

### Requirement: Existing Make bindings and gates remain mandatory

The Make finalizer and host gate SHALL independently rehash the complete normalized sealed Concept and effect evidence, require exact equality between stable Concept component keys and `product.json.components`, reject copied Concept pixels at any depth, bind the resulting Made contract to `concept_sha256` and `concept_effect_sha256`, and preserve the existing evidence-bound Make-to-Invent revision edge.

No simplified authoring marker SHALL waive early proof, print preflight, final product renders, blind signature review, integrated CAD verification, Quest Playtest, Release manual validation, or authenticated publication.

#### Scenario: Product matches normalized components
- **WHEN** each normalized stable component key appears exactly once in product metadata and all existing product checks pass
- **THEN** component correspondence can pass without reference to raw Invent files

#### Scenario: Normalized Concept is build-blocking
- **WHEN** exact Make evidence proves no conforming printable implementation can satisfy the sealed constraints
- **THEN** the existing Concept-bound revision request may return the run to Invent under the shared lifecycle budget
